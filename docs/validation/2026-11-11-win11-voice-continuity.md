# Win11 Wi-Fi 语音断续排查

用户反馈最新版通过 Wi-Fi 输入语音时声音不连续；输入法、音频驱动和现场日志尚不可用，不能确认现场根因。

## 已复现的问题

`AudioOutput` 使用 `blocksize=0`，主机可选择变化的回调长度。旧实现只等到 40 ms 数据就开始播放：若回调请求 60 ms，收到的 40 ms 会立即被播放，剩余 20 ms 被填成静音。启动与断流后的恢复都可能出现此情况。

回调长度的依据见 [sounddevice 官方文档](https://python-sounddevice.readthedocs.io/en/latest/api/streams.html)。没有把模拟的 60 ms 当成反馈用户机器上已经测得的值。

修复为等待「当前回调长度 + 40 ms 余量」后再启动，仍保留 500 ms 队列上限。录音结束使用原有 drain 路径送出不足预缓冲长度的尾音。电脑端修改，无固件协议变化。

新增回归覆盖 60 ms 回调与 80 ms 网络批次的连续非静音输入、启动等待、断流恢复和短句尾音。修复前的大回调测试明确失败，读出 40 ms 声音加 20 ms 静音。新增缺帧、播放缓冲不足和驱动欠载统计，录音结束写入活动日志，不保存音频。

## 验证范围

- `python -m unittest discover -s tests -p 'test_*.py'`：97 项通过。
- 主机 C 测试配置、构建及 `ctest --test-dir build-host --output-on-failure`：18 项通过。
- 新目录 `build-voice-win11-check` 的 ESP-IDF 5.5.3 / ESP32-C3 全量构建及 `idf.py -B build-voice-win11-check size`：通过。先用 `idf.py -B build-voice-win11-check build` 配置，分阶段编译后以 `cmake --build build-voice-win11-check -- -j 16` 完成；未沿用旧目录的固件产物。
- 初次桌面修复的应用二进制 1,739,008 字节，factory 分区余量 1,406,720 字节；DRAM 使用 240,756 字节，静态报告剩余 80,540 字节，与之前验证记录一致。无新增编译警告。保留原有 recovery 分区命名提示，以及完整应用超过 1 MB recovery 分区的容量提示；该阶段未修改分区或刷写设备。
- 首次配置发现本机 SDK 缺少 mbedTLS 等依赖源码，从原官方 5.5.3 安装归档补齐缺失文件并通过 ZIP CRC 校验后重新构建。本机虚拟音频输出枚举为空，无法运行真实虚拟音频回环。

原反馈用户的 Win11、路由器和输入法组合尚未复测；20 次重连及 30 分钟稳定性仍 NOT RUN。此修复不能恢复已丢失的采样，也不能消除持续网络中断。修改尚未打包或发布。

## 后续本机设备联调

用户安装 VB-CABLE 并启用讯飞输入后，实际路径为 LAN → CABLE Input / Windows WASAPI。旧会话出现缺帧及多次播放缓冲不足，驱动欠载计数为 0。待机轮询可达约 140～672 ms；源码已在设备录音时关闭 Wi-Fi 省电，因此不能据此将待机时延当作录音时延或直接归因省电。

先开启监测再由用户启动的连续录音已复现中断：电脑收到约 40 ms 音频后，后续设备回复超过 5 秒超时，电脑事件循环最大延迟约 10 ms。状态接口在等待请求完成期间保持上一次样本，不能将重复的 265 ms 状态误认为不断收到新音频。原始统计仅保存在仓库外，未保存音频。

USB 查询仍响应，无观察到的重启或 panic；设备可用堆约 15 KB。系统所选设备路由走 WLAN，而非 FlClash 虚拟网卡。上述信息尚不足以区分设备、无线链路或收发阻塞的根因。

为继续定位，在 `buddy_lan.c` 增加 USB 只读收发阶段、字节数、错误码、Wi-Fi RSSI 和省电状态统计，不留存载荷或密钥。增量诊断构建通过，18 项主机测试通过，应用大小 1,740,160 字节。刷写前已在仓库外以用户专用文件权限备份完整 8 MB 闪存，并核对分区一致；仅写入 0x10000 应用区域，校验通过，未改配网、配对、设备身份或 recovery 区域。诊断启动查询正常、无观察到的 panic；待机 RSSI 约 -72～-77 dBm。

诊断固件下捕捉到一次正常手动结束的录音，用户反馈「没有中断」。该次没有 5 秒通信超时；录音时省电状态为 WIFI_PS_NONE，RSSI 约 -64～-67 dBm，socket 错误码为 0。轮询样本最小 16 ms、中位数 172 ms、最大 1484 ms；结束状态仍记录缺帧 29、播放缓冲不足 52 次、驱动欠载 0。之后另一次录音的活动日志记录缺帧 11、播放缓冲不足 82 次、驱动欠载 0，也为手动结束。后一次未包含在同一份 USB 过程采样中，不能混为同一录音。

用户随后确认测试时没有移动设备，不能将本次改善归因于主动靠近路由器；无线信号本身仍可能波动。

结论：长时间收不到回复的中断本轮未复现，但音频连续性指标仍有异常；用户主观改善不能视为零丢帧或完整验收。重启和更换诊断固件同时发生，不能将改善单独归因于只读诊断代码或重启。设备保留诊断固件。本节记录诊断阶段；后续版本说明见 [v0.2.6](../releases/v0.2.6.md)。
